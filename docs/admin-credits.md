# Администрирование кредитов

Первый этап: поиск пользователя по email/UID и начисление компенсации бонусными кредитами без срока действия. Возврат по исходному списанию и исправление исторических расхождений — отдельные операции, в этот этап не входят.

## Доступ

Право `creditsAdmin: true` хранится в Firebase Auth Custom Claims. Cloud Function `adminCredits` при каждом запросе читает актуальный аккаунт администратора через Admin SDK: старый ID token не позволяет обойти отзыв права. Отключённые аккаунты не могут начислять или получать компенсации. Клиентские claims управляют только видимостью пункта меню.

На Windows скрипт может использовать существующий `firebase login`: передать `--firebase-cli`. Он обращается к установленному глобально Firebase CLI и не выводит или сохраняет токены. Для нестандартной установки путь к пакету `firebase-tools` задаётся через `FIREBASE_CLI_PATH`. Учётная запись Google должна иметь право управлять Firebase Auth проекта.

Без этого флага используются Application Default Credentials. `firebase login` сам по себе не настраивает ADC. Альтернатива — `gcloud auth application-default login` либо ключ служебного аккаунта через `GOOGLE_APPLICATION_CREDENTIALS`. Ключ хранится вне репозитория и не попадает во фронтенд.

Из корня репозитория сначала проверить найденный аккаунт:

```powershell
node functions/scripts/set-credits-admin.cjs --project milestis --email YOUR_EMAIL --grant --firebase-cli
```

Команда без `--apply` только показывает проект, UID, email и предполагаемое действие. После проверки выполнить ту же команду с `--apply`. Вместо `--email` можно передать `--uid`. Другие Custom Claims сохраняются.

Отзыв доступа:

```powershell
node functions/scripts/set-credits-admin.cjs --project milestis --uid USER_UID --revoke --firebase-cli --apply
```

После назначения открыть `/ru/account/admin-credits` и нажать «Обновить права доступа» либо войти заново. В настройках появится пункт «Начисление кредитов». Для административного аккаунта рекомендуется двухфакторная аутентификация.

## Начисление

1. Найти пользователя по email или UID.
2. Проверить имя, email, UID, баланс и доступные кредиты.
3. Ввести целое количество от 1 до 100 000 и причину от 3 до 500 символов.
4. Проверить карточку подтверждения и нажать «Начислить кредиты».

Сервер сам выбирает источник `bonus` и записывает в историю инициатора, получателя, причину, время, сумму и баланс после операции. В пользовательской истории операция подписана «Компенсация: бонусные кредиты». Причина хранится в `meta.note`, инициатор — в `meta.adminUid`, тип — `admin_adjustment`, `meta.reason` — `support_compensation`.

Баланс, партия кредитов и история обновляются одной транзакцией общего движка. Идентификатор запроса привязан к администратору; повтор с изменённой суммой, получателем или причиной отклоняется.

Перед отправкой интерфейс сохраняет запрос в sessionStorage. При потере ответа или перезагрузке этой вкладки повторяется тот же запрос. Не следует закрывать вкладку с неопределённым результатом и начинать новую операцию: сначала нужно завершить проверку либо сверить историю. Несколько намеренно созданных операций в разных вкладках считаются разными начислениями.

Если баланс расходится с `creditLots`, карточка показывает необходимость сверки и блокирует начисление. Компенсация не исправляет прежнее ручное изменение `users.balance`.

## Развёртывание и проверки

Развернуть Cloud Function `adminCredits` и обновлённый фронтенд. Новые Firestore rules и индексы для этой функции не нужны: записи выполняет только Admin SDK. Старый неэкспортируемый `adminManualAdjustment` заменён единым административным API; прав `admin`/`support` для него недостаточно.

Тесты `tests/admin-credits.test.mjs` проверяют права, их отзыв, поиск, валидацию, атомарность, повтор запросов, конфликт параметров, ошибки базы и сохранение остальных claims при назначении роли. `tests/admin-credits-ui.test.mjs` проверяет доступ к странице, переводы и восстановление незавершённого запроса. Тесты не выполняют реальные начисления.
